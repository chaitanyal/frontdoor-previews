# Astro Migration Plan

## Objective

Migrate the FrontDoor Health marketing site, shared practice previews, and standalone
practice websites from custom HTML transformation code to Astro while preserving the
current static-hosting model and all existing business behavior.

The migration is complete only when:

- `frontdoor.health` is generated by Astro.
- Standalone practice sites such as `drdronavalli.com` are generated by Astro.
- Shared previews continue to be generated at
  `/previews/<practice-slug>/`.
- Preview sites are excluded from sitemaps and protected from indexing through both
  HTML metadata and Cloudflare `_headers`.
- Production sitemap, robots, canonical, social metadata, and JSON-LD behavior is
  preserved.
- CTA, preview page-view, UTM attribution, preview-request, and Google Ads conversion
  tracking is verified end to end.
- Static output continues to deploy to Cloudflare Pages without an Astro server
  runtime.
- Existing build commands remain compatible, or are deliberately replaced only at
  the final cutover.

## Migration principles

1. **Run Astro beside the legacy renderer.** Do not replace the current build until
   semantic, visual, analytics, and deployment parity have been demonstrated.
2. **Do not combine framework migration with redesign.** Preserve content, layout,
   responsive behavior, Tailwind version, analytics behavior, URLs, and metadata.
3. **Keep `practice.json` as the practice content source.** Do not redesign its schema
   during the migration.
4. **Keep the current Python practice validator initially.** Astro must call
   `scripts/validate_practice_json.py`; schema consolidation can happen after the
   migration.
5. **Use Astro's static output.** Do not add SSR, an Astro Cloudflare adapter, React,
   Vue, or another client framework.
6. **Ship no hydrated islands unless a parity requirement cannot be met with static
   HTML and small scripts.**
7. **Preserve analytics scripts before refactoring them.** The first Astro version
   should copy the existing runtime files without behavioral changes.
8. **Keep the analytics Worker and D1 schema out of the rendering migration.**
   `worker/`, its migrations, and its deployment are not to be rewritten.
9. **Keep the Pages Function for preview requests unchanged.**
   `functions/api/preview-request.js` must continue to serve
   `/api/preview-request`.
10. **Advance one milestone at a time.** A milestone is complete only when all of its
    exit checks pass.

## Automated verification standard

- Use `@playwright/test` with Playwright-managed Chromium for all automated
  migration checks that exercise rendered pages, layouts, responsive behavior,
  interactions, analytics, local assets, or network requests.
- Do not make automated migration verification depend on a system-installed browser
  or an interactive browser session.
- On a fresh development or CI environment, install the compatible browser with
  `npx playwright install chromium`. Do not commit browser binaries or caches.
- Prefer `file://` URLs in Playwright for static output and relative-asset checks.
  Use HTTP only for behavior that requires it, such as response headers, Pages
  Functions, or staging deployment checks.
- Keep build scripts, semantic manifest comparisons, and Python HTML validators as
  lower-level checks. Playwright tests may invoke them, but they do not need to be
  rewritten as browser code.
- Intercept analytics, Google Ads, form submissions, and other external requests in
  Playwright unless a milestone explicitly requires a controlled staging or
  production smoke test. Manual browser review is supplementary and never replaces
  a required Playwright check.

## Current behavior that is a migration contract

### Build targets

The following interfaces must continue to work through the cutover:

| Target | Command | Required output |
| --- | --- | --- |
| Marketing | `npm run build:marketing` | Marketing pages plus eligible previews in `dist/` |
| Production practice | `SITE_ID=<slug> npm run build:practice` | One practice at the domain root in `dist/` |
| One preview | `SITE_ID=<slug> npm run build:preview` | One practice under `dist/previews/<slug>/` |
| All previews | `npm run build:preview:all` | All eligible practices under `dist/previews/<slug>/` |

`sites/template` is never deployed. An "eligible preview" is a real practice whose
`practice.json` has `seo.allowIndexing === false`. An individual preview build must
reject a practice whose `seo.allowIndexing` is `true`.

The first practice exercised through the Astro preview pipeline must be North Hills
Psychiatry, using the slug `northhillspsychiatry`. Its single-preview build and
verification must pass before testing `SITE_ID=ALL` or including Astro-generated
previews in the marketing build.

### Analytics and event tracking

The following behavior is immutable during the migration:

- `shared/attribution.js` captures `utm_campaign`, stores it in local storage, and
  expires it after 60 days.
- `shared/analytics.js` posts JSON to
  `https://analytics.frontdoor.health/event` using `fetch()` with:
  - `Content-Type: application/json`
  - `keepalive: true`
- Do not replace this request with `navigator.sendBeacon()`. An
  `application/json` Blob previously caused CORS failures.
- Preview `page_view` events are sent only when the URL begins with
  `/previews/<practice-slug>/`.
- Practice CTA events require `window.FRONTDOOR_PRACTICE_SLUG`.
- Practice home and provider pages load attribution and practice analytics and define
  `window.FRONTDOOR_PRACTICE_SLUG`. Practice privacy and accessibility pages retain
  their current attribution-only behavior unless a separately approved analytics
  change is made.
- CTA markup continues to use `data-frontdoor-cta`.
- The supported CTA mapping remains:
  - `email` -> `email_click`
  - `phone` -> `phone_click`
  - `newPatient` -> `new_patient_click`
  - `existingPatient` -> `existing_patient_click`
  - `directions` -> `directions_click`
  - `resource` -> `resource_download`
- CTA payloads preserve `practice_slug`, `event_type`, `page_path`,
  `destination_url`, `referrer`, `title`, `session_id`, `visitor_id`,
  `timestamp`, and optional `utm_campaign`.
- Preview page-view payloads preserve `event`, `path`, `practice_slug`,
  `referrer`, `title`, `session_id`, `visitor_id`, `timestamp`, and optional
  `utm_campaign`.
- Local `file://`, `localhost`, and loopback browsing never emits analytics events.
- The marketing preview-request event is emitted only when
  `/api/preview-request` returns `{ ok: true, accepted: true }`.
- Honeypot responses with `accepted: false`, validation failures, and API failures do
  not emit `preview_requested` or Google Ads conversion events.
- The `preview_requested` analytics payload continues to include only
  `utm_campaign`, `page_path`, `referrer`, `title`, `timestamp`,
  `practice_name`, `specialty`, and `has_website`. It must not include the
  person's name, email address, full submitted website URL, Turnstile token, or other
  form contents.
- An accepted preview request calls
  `window.FrontdoorGoogleAds.trackGoogleAdsPreviewRequestConversion()`.
- The Google Ads conversion destination remains
  `AW-18297020270/AokmCOPin8ocEO6-2ZRE`.
- The Google Ads global tag remains on marketing pages and is not added to practice
  preview pages.
- `shared/attribution.js` loads before code that reads attribution.

The Worker allowlists in `worker/wrangler.toml` must continue to include every
production practice origin and slug before a practice site is deployed.

### SEO and indexing

- Every HTML page has exactly one non-empty `<title>`, one meta description, and one
  `<h1>`.
- Indexable pages have exactly one canonical URL.
- Marketing content pages are indexable and contain no `noindex`.
- Marketing `404.html` retains its current `noindex,nofollow` metadata.
- The marketing sitemap:
  - Uses `https://frontdoor.health`.
  - Includes indexable marketing `index.html` routes.
  - Excludes `404.html`.
  - Excludes every route under `/previews/`.
- Every preview page includes
  `<meta name="robots" content="noindex, nofollow">`.
- Every preview route is also covered by an `_headers` rule containing
  `X-Robots-Tag: noindex, nofollow`.
- Preview routes never appear in `sitemap.xml`.
- A preview-only build does not generate a preview sitemap. Its public `robots.txt`
  continues to point at `https://frontdoor.health/sitemap.xml`.
- An indexable production practice:
  - Uses `seo.siteUrl` for every canonical and absolute social URL.
  - Produces a sitemap containing all generated practice pages.
  - Produces a public `robots.txt` that links to that sitemap.
  - Contains no `noindex`.
  - Contains no `pages.dev` or `frontdoor-previews` URL.
- A non-indexable standalone practice keeps the current noindex behavior and does not
  publish its own sitemap.
- Provider pages retain valid provider JSON-LD. Marketing and practice home pages
  retain their existing structured data.

### Static output and assets

- Generated HTML, CSS, images, fonts, PDFs, `_headers`, `_redirects`, `robots.txt`,
  and `sitemap.xml` remain static files.
- Practice images and resources retain their existing relative URLs.
- Nested provider and legal pages resolve their assets correctly.
- `practice.json`, `marketing.json`, Markdown research files, `.DS_Store`, and
  build-only files are not published.
- Playwright can load built HTML through `file://` for automated layout and
  local-asset verification.
- `/shared/analytics.js`, `/shared/attribution.js`, and
  `/shared/google-ads.js` remain available in deployments.

## Target architecture

Use one Astro installation with target-specific entry directories and shared page
implementations. This prevents the marketing root route and standalone-practice root
route from conflicting.

```text
src/
  components/
    shared/
    marketing/
    practice/
  layouts/
    MarketingLayout.astro
    PracticeLayout.astro
  lib/
    assets.ts
    build-target.ts
    practice-data.ts
    seo.ts
    themes.ts
  pages/
    shared/
      PracticeHome.astro
      ProviderPage.astro
      PracticePrivacy.astro
      PracticeAccessibility.astro
  entries/
    marketing/
      pages/
        index.astro
        about/index.astro
        case-studies/index.astro
        case-studies/[slug]/index.astro
        privacy/index.astro
        transformations/index.astro
        previews/[practice]/index.astro
        previews/[practice]/providers/[provider]/index.astro
        previews/[practice]/privacy/index.astro
        previews/[practice]/accessibility/index.astro
    preview/
      pages/
        previews/[practice]/index.astro
        previews/[practice]/providers/[provider]/index.astro
        previews/[practice]/privacy/index.astro
        previews/[practice]/accessibility/index.astro
    practice/
      pages/
        index.astro
        providers/[provider]/index.astro
        privacy/index.astro
        accessibility/index.astro
```

The exact directory names may change if Astro imposes a cleaner equivalent, but the
following separation is required:

- Shared visual components and page implementations are written once.
- Marketing, preview, and standalone-practice route entry points remain explicit.
- `FRONTDOOR_TARGET` and `SITE_ID` determine which entry directory, source data,
  `site`, output paths, and static assets are used.

During migration, Astro output goes to `.tmp/astro-dist/<target>/`. The legacy output
remains in `dist/` or is captured under `.tmp/legacy-dist/<target>/`. Only Milestone 7
may change the public build commands to emit Astro output directly into `dist/`.

Do not adopt Astro's image pipeline during this migration. Copy the current optimized
images and resources unchanged so URL shape, relative paths, local file verification,
and visual output remain stable.

Do not upgrade Tailwind during this migration. Preserve the existing compiled
practice stylesheet and existing marketing styling behavior first. Moving marketing
off the Tailwind CDN can be a separate, post-migration improvement.

## Rollback strategy

Until Milestone 8:

1. Keep the last known-good legacy build commands or a clearly named legacy wrapper.
2. Keep semantic and visual baselines.
3. Do not delete the legacy renderers.
4. For a staging failure, fix Astro without changing production.
5. For a production rendering or analytics regression:
   - Roll back the affected Cloudflare Pages deployment.
   - Rebuild and deploy with the legacy renderer if necessary.
   - Preserve the failed Astro output and Playwright trace/network evidence for
     diagnosis.
6. Do not modify or roll back D1 data as part of a frontend rollback.

## Final definition of done

The migration is done when all of the following are true:

- Astro is the default static builder for marketing, previews, and practices.
- Existing build command interfaces still work.
- Marketing, preview, and standalone-practice route manifests are complete.
- Playwright analytics contract tests pass with exact payload assertions.
- Accepted preview requests still trigger the non-PHI analytics event and Google Ads
  hook exactly once.
- CTA events are confirmed from both a production preview and a production practice.
- Preview HTML and response headers both enforce `noindex, nofollow`.
- No preview is listed in any sitemap.
- Indexable production sites have correct canonicals, robots, sitemaps, social
  metadata, and JSON-LD.
- Static assets and nested routes work through deployment checks and Playwright
  local-file verification.
- No practice or marketing source JSON is published.
- The analytics Worker, D1 storage contract, and preview-request Pages Function
  continue operating without a migration-induced rewrite.
